# jp-bizdoc 表記統一・用語集ガイド

文書内の表記ゆれを統一し、プロジェクト・文書単位の用語集を整備するための指針。翻訳時の対訳運用は `translation.md`(`glossary.csv`)を参照。本ファイルは日本語文書内の表記統一・用語定義が対象。

## 1. 表記統一の原則

| 観点 | 方針 | 例 |
|---|---|---|
| 全角半角(英数字) | 英数字は原則半角に統一(見出し・型番等の慣例がある場合を除く) | Ｗｅｂ → Web、２０２６ → 2026 |
| カタカナ長音の有無 | 社内・業界の慣例が無ければ、JIS Z 8301(長音省略の慣行)より**長音を付ける表記**を既定とし、文書内で統一する | サーバ/サーバー → サーバー、ユーザ/ユーザー → ユーザー |
| 送り仮名 | 内閣告示「送り仮名の付け方」の本則に沿った表記に統一する。ゆれやすい語は個別に確認する | 取り組み/取組み/取組 → 文書内で1種類に統一(法令・帳票の慣例語(例: 届出・申込)は本則の例外として扱う) |
| 略語 | 初出時に正式名称を併記し、以降は略語で統一する | 「重要業績評価指標(KPI)」→以降は「KPI」 |
| 単位・記号 | 単位は文書内で表記を統一(全角/半角、記号/漢字)。数値と単位の間隔も統一する | 100% と 100パーセント の混在を避ける、"㎡"と"平米"の混在を避ける |

上表は既定であり、依頼者の指定(社内表記ガイドライン等)があればそちらを優先する。

## 2. 用語集のフォーマット

用語集を作成する際は、以下の列構成を基本とする(Excel/CSV化する場合も同じ列)。

| 用語 | 読み | 英語 | 定義 |
|---|---|---|---|
| 稟議書 | りんぎしょ | approval request | 社内の決裁を得るための起案文書。 |
| 議事録 | ぎじろく | meeting minutes | 会議の決定事項・宿題事項を記録した文書。 |

- 「読み」は初見の読者・非母語話者向けの振り仮名(必要な語のみでよい)。
- 「英語」は資料の英訳・海外拠点との共有を想定した対訳(不要なら省略可)。
- 「定義」は1〜2文の簡潔な説明。社内固有の意味がある語は、それを反映する(例: 自社の稟議の位置づけ)。

## 3. 代表的な表記ゆれ(検出されやすい/されにくい)

| 種別 | 例 | `jp_glossary.py` での検出 |
|---|---|---|
| カタカナ長音の有無 | サーバー/サーバ、ユーザー/ユーザ、コンピューター/コンピュータ | **高精度で検出できる**(`variants` サブコマンド)。長音の有無で見出し語を正規化して突き合わせている。 |
| 全角半角(英数字) | Ｗｅｂ/Web、ＩＤ/ID、２０２６/2026 | **高精度で検出できる**(`variants`)。NFKC正規化で見出し語を揃えて突き合わせている。 |
| 送り仮名 | 取り組み/取組み/取組、申し込み/申込み/申込 | **連続した文章では、`variants` はほとんど検出できない**。見出し語の切り出しが漢字+後続のひらがな・助詞・活用語尾まで丸ごと拾ってしまうため、同じ語でも文中の位置によって異なるキーになりやすい。**送り仮名のゆれは`jp_glossary.py`に頼らず、Claudeが文書を読んで文脈から判断する**。 |
| 同義語・言い換え | 「弊社」/「当社」、「対応」/「対処」 | **検出されない**(表記のゆれではなく語彙選択の問題)。文書を読んで判断する。 |
| 略語と正式名称 | KPI/重要業績評価指標 | `terms` サブコマンドで頻出語の**候補**(カタカナ・英字・漢字)は拾えるが、どれが略語でどれが正式名称かの対応付けはしない。Claudeが対応関係を整理する。 |

`jp_glossary.py` はあくまで**機械的な候補抽出**(表記ゆれ候補・頻出語候補)にとどまる。統一すべきかどうかの最終判断、用語集の「読み」「英語」「定義」の記入は、文脈を踏まえてClaudeが行う。
