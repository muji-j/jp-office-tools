# jp-excel 落とし穴カタログ

日本語データ特有の「文字コード」「表記揺れ」「Excel の自動変換」に起因する典型的な事故を、
**症状 → 原因 → 対処** の3行構成でまとめる。実務でエラーや不一致に遭遇したら、まずここを検索する。

## 1. 文字化け(CP932 vs UTF-8)

- **症状**: BOM なしの UTF-8 CSV を Excel で開くと、日本語部分が「譁?怀」のような記号列に化ける。
- **原因**: Excel は BOM のない CSV を既定でシステムのロケール(日本語版なら CP932/Shift-JIS)として読み込むため、UTF-8 のバイト列を CP932 として誤解釈する。
- **対処**: `jp_excel.py detect` でまず実際のエンコーディングを確認したうえで、`clean --encoding-out utf-8-sig` で BOM 付き UTF-8 を出力するか、配布先が UTF-8 に対応しない場合は `--encoding-out cp932` で CP932 のまま出力する。判別はスクリプト内で BOM → UTF-8(厳密) → CP932 → EUC-JP の順に試行しており、`detect` の出力にはどの根拠で判定したかが併記される。

## 2. Shift-JIS と CP932 の違い

- **症状**: `～`(全角チルダ、U+FF5E)や丸数字・ローマ数字などが、環境によって別の文字化けを起こす、または変換に失敗する。
- **原因**: これらはJIS規格外の「機種依存文字(NEC選定IBM拡張文字など)」であり、狭義の Shift-JIS には定義がない。Windows で広く使われる CP932 はこれらを独自に収録した拡張文字集合であり、両者は厳密には別物。
- **対処**: 日本語 Windows 環境のデータを前提とするなら、エンコーディング指定は `shift_jis` ではなく `cp932` を使う(本ツールの `clean --encoding-out cp932` も CP932 を採用)。機種依存文字は環境間でやり取りする前提のデータには極力使わない運用が望ましい。

## 3. 全角数字・全角スペース

- **症状**: 見た目は同じ「123」なのに突合や集計で別グループとして扱われる、キー結合で一致しない。
- **原因**: `１２３`(全角数字)や全角スペースが半角の数字・スペースと文字コード上は別の文字として存在し、文字列としては不一致になる。目視では区別しづらい。
- **対処**: `clean` を通して NFKC 正規化を適用する(全角数字→半角、全角スペース→半角スペース)。突合・集計の前処理として必須。

## 4. 半角カナ

- **症状**: `ｶﾅ` のような半角カタカナを含む列が、クレンジング後に全角カタカナ(`カナ`)へ変わってしまう。
- **原因**: NFKC 正規化は半角カタカナを全角カタカナへ統一する仕様であり、`clean` の NFKC 処理も同様に働く。
- **対処**: 名簿システムやバーコード連携など、半角カナを意図的に使っている列がある場合は、クレンジング前後で差分(`cells_nfkc` の件数やレポート)を確認し、当該列は正規化の対象から外す、または変換後に元の表記へ戻す運用を検討する。

## 5. NFKC の副作用

- **症状**: クレンジング後に `㈱`が`(株)`に、`①`が`1`に、`②`が`2`のように、意図せず社名や項番の表記が変わってしまう。
- **原因**: NFKC(互換等価分解+正規化合成)は数字・カナだけでなく、`㈱`のような合字や丸数字・ローマ数字といった互換文字も対応する通常表記へ展開する仕様のため。
- **対処**: 社名・契約書の正式表記や項番の見た目を保持したい列は、`clean` を通す前に別列へ退避しておくか、クレンジング後にレポートの `cells_nfkc` 件数を見て変換有無を確認し、必要な列だけ原本の値に戻す。全列一括のクレンジングを鵜呑みにしない。

## 6. 和暦表記の揺れ

- **症状**: 同じ日付を指す値が `令和6年4月1日` / `R6.4.1` / `H31.1` のように列内でバラバラに入力されており、日付として扱えない・ソートできない。
- **原因**: 和暦は元号の正式表記・略記・区切り文字(`.`/`/`/漢字)が混在しやすく、入力者や台帳の年代によって書式が統一されていない。
- **対処**: `clean` は和暦文字列を ISO 8601(`YYYY-MM-DD`)へ変換するが、**セルの値全体が和暦表記と完全一致する場合のみ**変換される(「備考: 令和6年4月1日受領」のように和暦が文中に埋め込まれたセルは対象外で、元の文字列のまま残る)。埋め込み型の日付を抽出したい場合は、対象列を分割する、または `jp-dates` スキルのスクリプトで個別に変換する。

## 7. Excel の日付自動変換

- **症状**: CSV を Excel で開いただけで `4/1` が `2024/4/1` のような日付型になる、`001` という文字列コードが `1` に変わってしまう。
- **原因**: Excel はセルの見た目のパターンから型を推測し、日付らしい文字列や先頭ゼロ付き数値を自動的に日付型・数値型へ変換する仕様のため、CSV を開いた/保存した時点で元の文字列表現が失われる。
- **対処**: Excel で直接開かず、pandas 側で `dtype=str` を指定して文字列のまま読み込む(本ツールの `_read`/`clean` も CSV・xlsx とも `dtype=str` で読み込む方針)。必要な列だけ明示的に `pd.to_datetime` や `pd.to_numeric` で変換する。

## 8. セル結合

- **症状**: 見出しや部門名を結合セルで表現した表を pandas で読み込むと、結合範囲の先頭セル以外が `NaN`(空欄)になる。
- **原因**: Excel の「セルの結合」は表示上の見た目であり、値は左上の1セルにしか保持されない。pandas はそのまま読み込むため、結合されていた残りのセルは欠損として扱われる。
- **対処**: 元データ側でセル結合を解除してから読み込む、またはやむを得ず結合済みのファイルを扱う場合は読み込み後に対象列へ `ffill()`(前方向の値で埋める)を適用してから集計・突合を行う。

## 9. 数値の文字列化(左揃え数値)

- **症状**: 見た目は数値なのに `sum()` や `groupby().sum()` の結果が `0` になる、または列全体が文字列として連結されてしまう。
- **原因**: CSV 由来のデータやコピー&ペーストにより、数値がセル内で「文字列」として左揃えのまま格納されている(Excel 上は数値に見えても実体は文字列)。`dtype=str` で読み込む本ツールの方針でも同様の状態になり得る。
- **対処**: クレンジング(全角数字→半角・空白除去)を先に通したうえで、集計対象列に `pd.to_numeric(series, errors="coerce")` を適用してから合計・平均などの数値集計を行う。

## 10. 郵便番号・電話番号の先頭ゼロ消失

- **症状**: `0120-123-456` や `03-1234` のような番号が `120-123-456` のように先頭の `0` が消える、郵便番号 `0912345` が `912345` になる。
- **原因**: Excel やpandasの数値型推論により、先頭ゼロ付きの数値文字列が数値として解釈され、数値としての先頭ゼロは意味を持たないため欠落する。
- **対処**: 郵便番号・電話番号列は必ず文字列型(`dtype=str`)で扱い、既に先頭ゼロが失われている場合は桁数がわかっている前提で `series.str.zfill(桁数)` により復元する。復元前に必ず正しい桁数の根拠(郵便番号は7桁など)を確認する。

## 11. CSV 区切り文字の罠

- **症状**: 住所や備考欄に含まれる読点・カンマのせいで列がずれて読み込まれる、あるいはタブ区切り(TSV)のファイルをカンマ区切りとして読んで1列に全データが入ってしまう。
- **原因**: 住所・備考など自由記述の値にカンマが含まれている場合、クォート(`"..."`)で囲われていないと区切り文字と誤認される。また拡張子が `.csv` でも実体はタブ区切りというファイルも存在する。
- **対処**: 読み込み前に先頭数行を目視し、区切り文字とクォートの有無を確認する(`detect` はエンコーディング判別のみで区切り文字までは判定しない点に注意)。`pd.read_csv` では必要に応じて `sep="\t"` を明示し、カンマを含む自由記述列がある場合は出力側でクォート(`quoting=csv.QUOTE_NONNUMERIC` 等)が効いているかを確認する。

## 12. クロス集計表(横持ち)vs 正規形(縦持ち)

- **症状**: 「月×商品」のように見出しが横に並んだクロス集計表(横持ち)を pandas でそのまま `groupby` しようとすると、月ごとの列を個別に指定しないと集計できず、コードが冗長かつ列追加のたびに壊れる。
- **原因**: 横持ち(ワイド形式)は人が一覧で見るには適しているが、プログラムでの集計・結合には列名に値が混在する縦持ち(ロング形式)の方が扱いやすい。人向けの帳票フォーマットとプログラム向けのデータ形式が一致していないために起きる。
- **対処**: 集計・突合の前に `pd.melt(df, id_vars=[...], var_name="月", value_name="値")` で縦持ちに変換してから `groupby`/`pivot_table` を行う。最終的な帳票出力の段階で改めて `pivot_table` により横持ちへ戻す。
